# Kilivana — final functionality migration audit

Audit date: 2026-10-15. Canonical branch `feature/android-backend-integration`, HEAD `8f9dded09f84912fd868b450d61985f240305164`. This is a source review and planning checkpoint, not completion of every marketplace feature. No application code, database records or schemas changed during this audit.

**Current team decision: every farmer-submitted product requires administrator approval before public visibility.** Historical documents describing this as PENDING TEAM DECISION are superseded by [the current decision and verification](18-product-approval-decision-and-verification.md). The policy for editing an already approved product is still unresolved. Existing pending records were not approved or changed.

## Evidence and interpretation

Paths below use C = this canonical repository; R = sibling `kilivana-backend`; A = sibling `FarmApp`. Java paths in the matrix are relative to `src/main/java/com/kilivana/`; C adds `backend/`. Controller and service names identify actual implementations, not just tables. “Both” means source functionality exists in both, not equivalent contracts or successful end-to-end execution. Missing means no equivalent implementation found in this source inventory. Proposed work has not been implemented.

Runtime/test evidence is [report 16](review/16-local-migration-backend-verification.md): 284 backend tests and 138 Android unit tests passed; Hibernate validation and actual farmer HTTP smoke tests passed after V16–V18. These were prior executions, not rerun for this documentation audit. Two insertion-based PostgreSQL tests were deliberately excluded from the existing database. Current GET-only checks again confirmed health and the pending-product exposure described in document 18. No approval, checkout, payment or inspection mutation was performed. No current physical-device, website or admin-frontend verification is claimed.

## What has actually moved

The working farmer slice now uses C's existing services: email registration/login, profile setup and account edits, categories, own listings, product create/edit, multi-image upload/retrieval and refresh. A implements the envelope/DTO adapter and safe numeric/money/quantity conversions; it is not an Android-specific backend. Most product/image functionality was already Daniel's and was reused rather than ported. C additionally contains the Phase 1 authorization, account-state, token-type, catalog-pricing and locking fixes. V16–V18 reconcile Daniel's newer model with the existing local data without inventing verification/quality values.

This does not establish whole-system functional parity or migration of the original database. The original source still contains real capabilities absent in C, and several demos remain deliberately disconnected. The canonical feature branch does not contain A's uncommitted implementation; coordinate its separate review so backend review is not mistaken for delivery of the Android code.

## Minimum remaining transfer scope and ownership

1. **Before public use:** close pending-listing/asset visibility and HTTP-method/category authorization gaps. Preserve private owner/admin access and A's pending catalog. This is enforcement of the newly agreed requirement, not all of Phase 2. Obtain implementation approval after this audit.
2. **Before calling farmer action parity complete:** agree and implement safe unlisting, or explicitly accept its deferral to Daniel. This is the main original farmer action currently disabled. Required tests: owner-only withdrawal, retained order/image history, public invisibility, no accidental approval on restore.
3. **Explicit transfer-or-defer list for Daniel:** saved products; contact inbox; secure refresh/recovery capability; seller-scoped order projection; structured inspection checklist/report/visit features; event-triggered notifications. Their source exists in R, but each needs C contracts/security and some need new reviewed migrations. None is silently marked migrated.
4. **Optional original capabilities:** badges and richer catalog metadata. Decide retention before spending migration effort; no working current farmer dependency established.

Daniel can own checkout completion, real payment/refund operations, delivery pricing/logistics deployment, full admin-reviewed inspection workflow, remaining client integration and all new chat functionality. These must not become a requirement that this contributor implement the entire marketplace before handing over. Record accepted deferrals rather than claim full parity.

## Architecture and retirement criterion

Android defaults to C at loopback8081 (`A/app/build.gradle.kts:7,27`; ApiClient canonical adapters). An explicit legacy build flag still exists, but it is not an approved workaround or default. Buyer/supplier/inspector screens import mock data; existing farmer roster, orders and destructive removal are explicitly unavailable in CanonicalFarmService. No Room/SQLite or Android-specific backend schema was introduced for this integration.

All clients should consume C and its single logical PostgreSQL database per environment. C already provides admin/ecommerce namespaces; actual website/admin code and deployments were not available in this review, so shared production integration is an architectural target, not a tested fact.

The reference backend can stop being an Android runtime dependency for the implemented farmer slice. Do not delete or retire its repository until the transfer-or-defer list is accepted, consumers and any retained data are inventoried, A's canonical build is delivered, and cross-client contracts are reviewed. No need to keep running a second permanent backend just to retain reference source.
