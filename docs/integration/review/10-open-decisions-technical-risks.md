## Possible risks and not-yet-verified behavior

- R refresh family revocation runs within @Transactional and then throws an authentication failure; durable replay-family revocation may roll back. Requires specific integration test; code intent is not proof of security. R webhook source verification also needs review; public callback locking/idempotency alone is not provider authenticity.
- C sold/reserved consumption across generic status/receipt/dispute/logistics flows needs full invariant tests. C dispute resolution updates bookkeeping but not proof of provider refund/stock release. Concurrent max+1 user/order reference generation can collide; database uniqueness prevents duplicate codes but may fail valid concurrent requests.
- Image upload/provider side effects are not one atomic DB/storage transaction; product upload failure/rollback can orphan external assets, replace/delete operations need reconciliation tests. Current database-provider test does not establish Cloudinary/local provider live reliability. Allowed MIME and size checks do not by themselves prove content inspection/security.
- C scalar relationship IDs and absent generated FKs increase orphan risk. Historical SQL patches plus entity definitions are not a migration baseline. Need staging schema discovery and reviewed baseline, not replay old scripts blindly. No schema comparison to production was performed.
- Reference decimal quantities, UUID keys, versioned entities, joins, CustomerOrder splits and evidence/token tables cannot be copied into canonical Long schemas. Actual source data wasn't exported/read; quantity/identity conflicts and import effort remain unknown.
- No actual e-commerce/admin frontend repositories were supplied/inspected; configuration, CORS, forms, JS Long precision, endpoint usage and end-to-end regressions remain unknown. JavaScript clients need an agreed numeric-ID handling contract before IDs exceed safe integer range.
- Local Android default HTTP loopback is a development transport, not a production configuration. No production data/infrastructure or account secrets were accessed. Remaining original backend clients outside named projects cannot be ruled out.
- Current 138 Android tests and prior physical smoke are bounded farmer evidence. No live negative-authorization, concurrency, report/admin review, checkout, payment sandbox, provider/refund, cross-client UI or data migration test was performed by this audit.

## Architecture confirmation and gates

The intended architecture is feasible and already demonstrated for Android farmer records: Android → C → existing local kilivana. C holds shared User/Product/Profile tables; there is no new Android schema or duplicated authoritative backend. Android encrypted session/photo drafts are local client state, not another marketplace database. R remains a separate reference backend, not part of the target deployment.

Website → C → same logical DB and Admin → C → same logical DB are **intended**, not verified frontend deployments. Each environment must have its own verified single canonical database identity and no hidden original-service calls. Access/moderation controls determine what each client sees; “shared” does not mean every role can read every record.

Do not retire R until required original behavior is supported or explicitly deferred, all actual clients point to C, data migration and reconciliation approved/tested, full authorization/state/concurrency/provider suites pass, and rollback/cutover owners agree. Before a PR: Daniel reviews business decisions and exact wire impacts, staging baseline/migrations, negative tests, real web/admin regressions, security and credentials hygiene, and separation of pre-existing uncommitted work. No commit/push/share/merge is authorized by this audit.

Additional confirmed ownership finding: `admin/controller/AddressController.java` maps both `/api/v1/users` and `/api/v1`; explicit `/{userId}/addresses` methods pass the path userId to AddressService without binding it to the principal. AddressService update/delete verifies address.userId equals the supplied userId, not the caller. Self-service aliases bind principal correctly, but do not secure the alternate paths. Include every alias in negative ownership tests.

Canonical mail capability: `mail/MailAdminController.java` POST `/api/v1/admin/mail/test` delegates to SendGridMailService and returns explicit configured/sent flags. It is admin-only and disabled in the local launcher; no message was sent by this audit. Reference `auth/service/SpringMailPasswordResetMailSender.java` uses JavaMailSender for reset links, fails if unconfigured. Neither source presence verifies actual external email delivery; retain canonical mail service and reuse it only after approved recovery integration and safe delivery tests.
