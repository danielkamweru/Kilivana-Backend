# Farmer Inspection and Verification Workflow Audit

> Review copy: historical evidence from the tested feature branch based on `a55b56e`, not an audit of current upstream `main`. Workstation paths/device identifiers are omitted. Original local documents are preserved outside this commit scope. See [review guide](README.md).

Audit date: 2026-10-14. This is source evidence, not a successful live inspection workflow. No inspection/verification/product state changed. Paths use the roots defined in [06](06-backend-feature-parity-matrix.md).

## Required workflow and finding

Required: farmer registers and creates farmer/farm profile → assigned inspector assesses → evidence/findings submitted → admin reviews submitted report → admin makes farmer verification decision. **Neither backend currently implements this complete, linked and enforced workflow.** Inspector recommendation must remain distinct from final admin approval. Product approval is separately **PENDING TEAM DECISION**; no new product rule is proposed as an assumed requirement.

## Exact canonical authorization findings

`admin/controller/InspectionController.java:34` maps **both** `/api/v1/admin/inspections` and `/api/v1/inspections`. `config/SecurityConfig.java` protects admin namespace but defaults remaining requests to authenticated. InspectionController has no @PreAuthorize, no AuthenticationPrincipal, and its service has no actor checks. Consequence from source: any authenticated role can use the non-admin alias to list/read/create/delete inspections, choose another inspectorId or target, alter status/result and add/remove evidence. This bypasses the admin prefix, although it does **not** directly change User.verificationStatus. No exploit mutation was executed.

`admin/service/InspectionService.java:createInspection/updateInspectionStatus/updateInspectionResult`: no target existence/type validation, inspector qualification/assignment validation, legal transition graph, final submission lock or optimistic concurrency. DTO @NotNull constraints do not execute without controller @Valid. `updateInspectionResult` uses enum valueOf (uppercase), unlike product lower wire enum mapping; invalid result becomes BadRequest. Result stamping does not update status to COMPLETED. `submitEvidence` routes to CHANGES_REQUIRED regardless of evidence purpose.

`admin/controller/AdminFarmerController.java:110` is protected by ADMIN namespace. Its actual approve/reject handlers mutate User directly, not the similarly named farm/service/AdminFarmerService. Both implementations have parallel behavior, but neither consumes a reviewed inspection. Rejection makes the account inactive; that effect must be preserved unless the team approves a change. The checked reason is not retained as an admin decision record. Current JWT request filter does not consult account state, so already-issued access tokens are not immediately invalidated by rejection/suspension.

`farm/controller/KycController.java` admin-only document approval is a separate operation; it does not verify the farmer or link inspection reports. Existing reviewedBy/reviewedAt fields are returned but approve/reject handlers do not set them. FarmerProfile.verificationInfo is owner-editable descriptive data and must not be trusted as final verification.

All database/provider images are publicly served through `/api/v1/images/**` and local uploads through `/uploads/**` per SecurityConfig. Random URLs are not authorization. Reusing public product image transport for sensitive inspection/KYC evidence needs an explicit privacy policy and protected retrieval design before live inspection rollout.

## Reference limitations to avoid copying

R InspectionService ties assessment to Product and uses current verified inspector; update/result only assigned inspector. SiteVisitService allows any verified inspector to schedule/complete any visit, not an assigned-inspector enforcement model. VisitPhotoService read permits any verified inspector or product owner. AuditReportService.requireViewer only checks inspector/seller role and does not scope reports to owning seller; admins are not accepted by that predicate. Report reads therefore need ownership and admin-review fixes even if selected behavior is reused.

R submitResult sends an InspectionCompletedEvent and pass auto-awards QUALITY_HARVEST; it does not constitute final farmer approval. R UserService admin verification is independent of report, just as C's manual decision is. Do not import automatic badge logic into farmer verification or product approval.

## Unverified farmer eligibility today

- C registration sets NOT_REQUIRED, not VERIFIED or PENDING. Product creation performs no farmer-verification check (nor strict farmer/supplier role restriction); created products are pending. R farmer defaults UNVERIFIED but createProduct permits farmers/suppliers and starts ACTIVE.
- C public general list/search only ACTIVE, but details/seller/category routes disclose records without consistent status filtering. Own seller may currently set status ACTIVE via PUT products/{id}/status. This is source-verified current behavior, not an approved publishing rule.
- C CartService/OrderService require ACTIVE product, not verified seller. Thus pending cannot be ordered via these implementations, while ACTIVE from an unverified seller can receive orders subject to buyer/address/stock validations. R ordering likewise has no farmer-verification gate.
- Android creates pending products and never calls owner status activation. It neither verifies farmer nor integrates real inspector recommendations/admin review. Inspector navigation VERIFIED gate is only for inspectors and does not answer farmer eligibility.

## Proposed minimum completion design — requires approval

Reuse canonical Inspection/Evidence/User/FarmerProfile/Farm records with an agreed authoritative target. Add controlled assignment/scheduledAt, structured findings/checklist/recommendation, explicit submitted revision, assigned-inspector-only writes, private evidence retrieval, admin review referencing report revision, reviewer identity/time/reason, retained decisions and audit. Recommendation names should unambiguously distinguish inspector assessment from administrator decision without silently changing existing wire enums. Add adapters/aliases if needed to preserve existing web/admin clients.

Any new columns/tables/indexes require a reviewed migration with environment identity verification and separate approval; no SQL was applied or generated as executable migration here. Avoid deleting/replacing existing inspection records. Keep current product approval behavior unchanged while this workflow is completed.

Acceptance tests: farmer cannot assign/approve; buyer/supplier cannot alter inspections; inspector cannot alter another assignment or submitted revision; invalid/missing targets rejected; evidence accessible only to authorized viewers; submit requires agreed findings/evidence; admin decision requires submitted report, retains actor/reason/revision, rejection effect explicit; recommendation never directly verifies user; history retained across reassessment; concurrent edits conflict safely; all three clients use same inspection ID and decision. These are proposed tests, not passing claims.
