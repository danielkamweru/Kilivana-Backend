## Scope and evidence standard

Repository roots: **C** = `kilivana-shared-backend`, **R** = `../kilivana-backend`, **A** = `../FarmApp`, all under `<workspace-root>/`. Inspected working trees, including uncommitted changes, at C `a55b56e`, R `627ed1e`, A `231b968`. HEAD alone does not describe the audited code. All existing work is preserved.

Paths below are relative to the indicated root. For compactness C Java paths start at `src/main/java/com/kilivana/backend/`; R Java paths start at `src/main/java/com/kilivana/`; A Kotlin paths start at `app/src/main/java/com/example/farmapp/`. Controller and service names in each row specify their package-relative files. API paths start with `/api/v1` unless explicitly stated. Entity references are domain/entity class names, not proof of complete behavior.

**FULLY SUPPORTED** means the bounded capability was implemented and exercised by the recorded local device tests, not production or whole-module parity. **PARTIALLY SUPPORTED** means useful implementation exists but behavior/security/integration gaps remain. **MISSING** means no equivalent found in the inspected canonical source. **INCOMPATIBLE** means materially different contracts or rules prevent substitution. **NOT YET VERIFIED** means source exists but sufficient end-to-end evidence is unavailable. **PENDING TEAM DECISION** is a business gate, never authorization to change behavior.

Prior runtime evidence: [05-local-demo-verification.md](05-local-demo-verification.md): 41 selected database-free backend tests; 138 Android unit tests; physical-device registration, profile creation, login, categories, own products, pending creation/editing, database-provider images, separate-process session restoration and refresh. Those are prior results, not newly run tests in this audit. Web/admin frontend source repositories were not supplied or found among the named sibling projects; frontend interoperability is **NOT YET VERIFIED**. No real payment provider, commerce, inspection, or logistics mutation was tested in this audit.

## Farmer verification versus product approval

**PENDING TEAM DECISION: individual product approval.** Preserve existing pending creation, visibility, purchasing and transitions until separately approved. Current C product status endpoint permits owner-set status; record this as a confirmed enforcement gap, not permission to silently change existing web/admin behavior.

Both backends permit farmer product creation without checking farmer verification. R creates ACTIVE; C creates pending. C pending cannot be ordered through createOrder/CartService ACTIVE checks. A C product made ACTIVE can receive orders without checking seller verification; public seller/category/detail endpoints can expose pending data. An unverified owner can currently call the C status endpoint to activate its listing (code verified, mutation not executed). No farmer-verification gate was found in R ordering either. These are current implementation facts, not agreed business policy.

If individual approval is required: owner activation permissions, review records, re-review after edits and consistent public filters need an approved policy and regression tests. If individual approval is not required: creation status and publishing eligibility still require an explicit team decision and rollout; pending records require a disposition plan. Neither choice follows automatically from farmer verification. See [08](08-farmer-inspection-verification-audit.md) and [10](10-open-decisions-technical-risks.md).

## Shared model compatibility and reuse

Use C as sole authoritative backend/database per environment. Reuse its User/role profiles, Product/Category/ProductImage, image providers, inspection/evidence primitives, admin farmer action, order items/events, cart/payment/dispute records and logistics/POD service. Add missing capabilities around them; do not transplant R UUID modules or create parallel Android tables.

Do not equate FarmerProfile with Farm, Farm.Crop with marketplace Product, InspectionResult.APPROVED with User.verificationStatus.VERIFIED, InspectorProfile.status with trusted inspector authorization, Payment.REFUNDED with real money returned, or a Cart marked CHECKOUT_PROCESSING with an Order. Each distinction affects migration and acceptance criteria.

Real web/admin frontends are not verified. Their existing envelopes, aliases, numeric IDs, lowercase enum serialization, profile/inspection/image forms, pagination, admin aggregates, payment enums and order reference codes must be captured from actual clients before contract changes. Android integration proves common records are feasible, not whole-platform parity.
